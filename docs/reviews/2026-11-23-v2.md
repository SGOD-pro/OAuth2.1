## Summary

This change completes acceptance of the first bounded runtime slice of OAuth V2 Slice P1b in `backend/src/utils/client-resolver.ts`, protocol entry routes, configuration simplification fixtures, and integration test suites. The canonical client representation exposes validated policy dimensions (`clientType`, `accessPolicy`, `classification`, `isAmbiguous`, `ambiguityReasonCodes`, `ambiguityReasons`) to all runtime callers. Incomplete client records without access metadata fail closed with ambiguous classification in `config-simplification.test.ts`. Ambiguous clients fail closed with endpoint specific errors: direct HTTP 400 at authorize without redirecting per RFC 6749 Section 3.1.2.4, direct HTTP 400 at consent and continuation, HTTP 401 at token code and refresh grants with Basic challenge headers on Basic authentication requests, HTTP 401 at introspect, HTTP 200 `{ active: false }` on authenticated introspection of tokens targeting ambiguous clients, HTTP 401 at revoke with authentication before mutation guaranteeing zero database changes, and HTTP 400 at initiation, email sign in, and email sign up. Meaningful HTTP compatibility is verified across all four valid client combinations (Class A open public, Class B private confidential, Class C open confidential, Class E private public) using the installed Better Auth engine and disposable MongoDB, confirming authenticated authorization, code issuance, explicit private membership enforcement, and RS256 JWT signature and subject verification. Both enforcement and compatibility suites are integrated into `.github/workflows/ci.yml` and `backend/package.json`.

## Findings and Assessment

1. Incomplete Client Configuration Simplification: In `backend/tests/unit/config-simplification.test.ts`, the incomplete client fixture assertion was updated from legacy `isPublic: true` to assert fail closed behavior (`isPublic: false`, `is_public: false`, `isAmbiguous: true`, `classification: "AMBIGUOUS"`, `accessPolicy: "private"`, `reasonCodes: ["MISSING_ACCESS_METADATA"]`). Null handling, default derivation, and metadata preservation remain intact.
2. Four Class HTTP Compatibility: In `backend/tests/security/client-policy-compatibility.test.ts`, end to end HTTP compatibility is proven for all four valid client combinations using the installed engine and disposable MongoDB.
   * Class A (Open Public): authenticated authorization, code issuance, token exchange using PKCE and no client secret, and RS256 token verification.
   * Class B (Private Confidential): unassigned user denied at authorize with HTTP 302 access denied redirect, assigned user authorized with code issuance, token exchange via Basic authentication credentials, and RS256 token verification.
   * Class C (Open Confidential): authenticated authorization, code issuance, token exchange via Basic authentication credentials, and RS256 token verification.
   * Class E (Private Public): unassigned user denied at authorize with HTTP 302 access denied redirect, assigned user authorized with code issuance, token exchange using PKCE and no client secret, and RS256 token verification.
3. Basic Authentication Challenge Header: In `backend/src/routes/auth-token-auth.ts`, `backend/src/routes/auth-revoke.ts`, and `backend/src/routes/auth-introspect.ts`, ambiguous client rejection returns HTTP 401 with `WWW-Authenticate: Basic realm="OAuth"` when caller presents Basic authorization headers.
4. Introspection Target Client Security: In `backend/src/routes/auth-introspect.ts`, authenticated inspection of a token targeting an ambiguous client returns HTTP 200 `{ active: false }`, ensuring expired or revoked client configurations cannot yield active tokens.
5. Canonical Client Policy Representation: In `backend/src/utils/client-resolver.ts`, `CanonicalOAuthClient` carries `clientType`, `accessPolicy`, `classification`, `isAmbiguous`, `ambiguityReasonCodes`, and `ambiguityReasons` resolved via `resolveClientPolicy`. Runtime callers access these validated properties directly without importing classifier internals.
6. Direct Authorization Denial Without Redirect: In `backend/src/routes/auth-authorize.ts`, ambiguous clients are rejected with HTTP 400 `invalid_client` directly, adhering strictly to RFC 6749 Section 3.1.2.4. No redirect to unverified callback URIs is performed.
7. Authentication Before Mutation on Revocation: In `backend/src/routes/auth-revoke.ts`, ambiguous caller clients are rejected with HTTP 401 `invalid_client` before calling the engine handler or executing token deletion queries. Disposable MongoDB verification proves zero database modifications.
8. CI Workflow Integration: The new suites `test:client-policy-enforcement` and `test:client-policy-compatibility` run in `.github/workflows/ci.yml` and `test:unit` in `backend/package.json`.
9. Pending Enforcement Boundaries: Later Slice P1b items (mandatory PKCE challenge on confidential code authorization, public refresh rotation verifier removal, and bypass flag removal of ambient `user_app_registrations` writes) and Slice P1c administrative UI remain explicitly pending.
