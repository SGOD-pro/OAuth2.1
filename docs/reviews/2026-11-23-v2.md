## Summary

This change implements the first bounded runtime slice of OAuth V2 Slice P1b in `backend/src/utils/client-resolver.ts` and protocol entry routes, while correcting the deployment rollback compatibility matrix in `docs/specs/0008-multi-account-identity-platform/0008-p1-client-policy-migration.md`. The canonical client representation now exposes validated policy dimensions (`clientType`, `accessPolicy`, `classification`, `isAmbiguous`, `ambiguityReasonCodes`, `ambiguityReasons`) to all runtime callers. Ambiguous clients fail closed with endpoint specific errors: direct HTTP 400 at authorize without redirecting per RFC 6749 Section 3.1.2.4, direct HTTP 400 at consent and continuation, HTTP 401 at token code and refresh grants, HTTP 401 at introspect, HTTP 401 at revoke with authentication before mutation guaranteeing zero database changes, and HTTP 400 at initiation, email sign in, and email sign up. Clean legacy clients across all four combinations continue to proceed normally. The deployment rollback matrix accurately documents that P1a does not enforce ambiguity at runtime and that the open access bypass flag does not align client authentication across mixed versions.

## Findings and Assessment

1. Deployment Rollback Compatibility Matrix: Section 4.7 Procedure 3 in `0008-p1-client-policy-migration.md` is corrected to eliminate unconditional rollback guarantees. The updated matrix documents that P1a binaries evaluate legacy fields only and do not deny ambiguous records at runtime. Draining incompatible nodes during rolling deployments and disabling ambiguous records (`disabled: true`) in MongoDB prior to binary downgrade are explicitly required.
2. Canonical Client Policy Representation: In `backend/src/utils/client-resolver.ts`, `CanonicalOAuthClient` now carries `clientType`, `accessPolicy`, `classification`, `isAmbiguous`, `ambiguityReasonCodes`, and `ambiguityReasons` resolved via `resolveClientPolicy`. Runtime callers access these validated properties directly without importing the classifier into protocol routes, preserving the architectural boundary established in P1a.
3. Direct Authorization Denial Without Redirect: In `backend/src/routes/auth-authorize.ts`, ambiguous clients are rejected with HTTP 400 `invalid_client` directly, adhering strictly to RFC 6749 Section 3.1.2.4. No redirect to unverified callback URIs is performed.
4. Authentication Before Mutation on Revocation: In `backend/src/routes/auth-revoke.ts`, ambiguous caller clients are rejected with HTTP 401 `invalid_client` before calling the engine handler or executing token deletion queries. Integration testing against disposable MongoDB verifies that existing token family and access token documents experience zero modifications when an ambiguous client calls revocation.
5. Introspection Boundary Security: In `backend/src/routes/auth-introspect.ts`, ambiguous caller clients are rejected with HTTP 401 `invalid_client`. When a valid confidential caller inspects a token whose target client is ambiguous, introspection returns HTTP 200 `{ active: false }` per RFC 7662 Section 2.2, preventing ambiguous clients from surviving as active authorization subjects.
6. Consent, Continuation, and Prelogin Boundaries: Direct HTTP 400 `invalid_client` rejection is enforced in `auth-consent.ts` for consent and continuation, `auth-initiate.ts` for prelogin client validation, and `auth-sign-in.ts` and `auth-sign-up.ts` for email credential operations.
7. Clean Legacy Client Compatibility: Clean legacy records (Class A open public, Class B private confidential, Class C open confidential, Class E private public) resolve without ambiguity and continue through authorization code issuance and login redirection without interruption.
8. Pending Enforcement Boundaries: Later Slice P1b items (mandatory PKCE challenge on confidential code authorization, public refresh rotation verifier removal, and bypass flag removal of ambient `user_app_registrations` writes) and Slice P1c administrative UI remain explicitly pending.
