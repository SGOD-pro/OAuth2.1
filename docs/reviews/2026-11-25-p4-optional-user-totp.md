# Review, v2, 2026-11-25

**Reviewed by**: review subagent (author on parent session, model unrecorded)

## Summary

Commit `39209af` fixes the fallback bug in `createRateLimiter` when `keyFn` returns `null`, domain separates recovery email quota digests, and tightens loop assertions in `p4-backup-code-recovery.test.ts`. Commit `562751a` adds owner dashboard TOTP management (`/api/identity/totp/enable`, `/verify`, `/disable`), a `totp_used_steps` replay guard, `AccountTotpPanel.tsx`, and `p4-optional-user-totp.test.ts`. While request context binding and the recovery quota fixes are sound, TOTP disable destroys the rotated current session, fails to revoke `ObjectId` keyed refresh tokens and refresh families, and leaves TOTP replay protection bypassable across the 90 second engine window and completely absent on login.

## Blockers

### 🔴 Disabling TOTP deletes the current rotated session and breaks browser session binding, `backend/src/routes/identity-totp.ts:205-224`
**Problem**: Calling `authProvider.api.disableTwoFactor` in Better Auth (`backend/node_modules/better-auth/dist/plugins/two-factor/index.mjs:227-231`) creates a new session and deletes the incoming `verified.sessionId`. `handleOwnerTotpDisable` discards the `Set-Cookie` header from `disableTwoFactor`, leaves `browser_session_sets` pointing to the deleted `verified.sessionId`, and then runs `deleteMany` excluding only `verified.sessionId`, which deletes the newly rotated session too.
**Why it matters**: Disabling TOTP silently logs the user out of their current active browser session instead of revoking only other sessions as required by `docs/SESSION_MODEL.md`, and leaves `browser_session_sets` referencing a nonexistent session ID.
**Suggested fix**: Extract the rotated session token from `res.headers` using `extractSessionTokenFromHeaders`, look up the new session ID, atomically update the active `browser_session_sets` entry (matching `entryId`, old `sessionId`, and `status: "active"`), exclude the new session ID in `deleteMany`, revoke `context.contextId` in `identity_contexts`, and assert in tests that the current session survives while other sessions for that user are deleted.

### 🔴 Disabling TOTP misses `ObjectId` keyed `oauthRefreshToken` rows and leaves `oauth_token_families` active, `backend/src/routes/identity-totp.ts:221`
**Problem**: Line 221 deletes from `oauthRefreshToken` using only `{ userId: verified.userId }` as a string, and never updates `oauth_token_families` or `oauthAccessToken`. In `@better-auth/oauth-provider` (`authorize-Crqw4_bR.mjs:3933-3937`) and `@better-auth/mongo-adapter` (`index.mjs:513-533`), `oauthRefreshToken.userId` references `user.id` and is coerced to a `MongoDB ObjectId` on write.
**Why it matters**: Refresh tokens created by Better Auth with an `ObjectId` `userId` survive TOTP disable, and leaving `oauth_token_families` in `status: "active"` allows existing access tokens to keep passing `oauth_token_families` checks in `/api/auth/oauth2/userinfo` and `/api/auth/oauth2/introspect`, violating `docs/SESSION_MODEL.md`.
**Suggested fix**: Query `oauthRefreshToken` and `oauthAccessToken` using both string and `ObjectId` representations of `verified.userId`, and mark matching `oauth_token_families` documents as `status: "revoked"` with `revokedAt` set.

### 🔴 TOTP replay guard is bypassable across adjacent steps, split by purpose, and missing from login and admin endpoints, `backend/src/identity/totp-replay-guard.ts:31-60`
**Problem**: Better Auth verifies TOTP via `@better-auth/utils` (`otp.mjs:41-58`) with `window = 1`, accepting three 30 second steps (90 seconds total). `claimTotpTimeStep` records only the current wall clock `step` (`Math.floor(Date.now() / 1000 / 30)`) keyed by `{ userId, step, purpose }`. Thus a code accepted in step `S` can be replayed in step `S + 1` while `S` is still valid inside `window = 1`, and can also be reused across `"enroll"`, `"login"`, and `"disable"` in the same step. In addition, `identity-totp.ts:108-124` and `189-204` claim the step before verifying the code (so an invalid guess temporarily blocks a concurrent valid code and an exception leaves the step locked for 5 minutes), and `handleVerifyTotp` in `backend/src/routes/auth-two-factor.ts:19-66` never invokes the replay guard at all.
**Why it matters**: Captured TOTP codes can be replayed across step boundaries on dashboard enrollment/disable and replayed freely during login and admin TOTP verification (`POST /api/auth/two-factor/verify-totp`).
**Suggested fix**: Verify which exact counter offset (`-1`, `0`, `+1`) matched and atomically advance or record the matched counter step without `purpose` splitting (for example via a monotonic CAS `lastAcceptedStep < matchedStep` guard), never pre lock on unverified guesses, and enforce the same replay guard in `handleVerifyTotp`.

### 🔴 Enrolled user login 2FA bypasses `browser_session_sets` and inherits Better Auth ambient session fallback, `backend/src/routes/auth-two-factor.ts:19-66`
**Problem**: Password sign in (`auth-sign-in.ts:186-218`) skips `attachOrdinaryBrowserSessionToResponse` when `twoFactorRedirect` is returned, while `handleVerifyTotp` and `handleVerifyBackupCode` only call `resolveVerifiedMfaSession` (`auth-two-factor-context.ts:175-214`) and never attach the completed session to `browser_session_sets`. Furthermore, Better Auth `verifyTwoFactor` (`verify-two-factor.mjs:14-116`) resolves `getSessionFromCtx(ctx)` before `better-auth.two_factor`, so if an ambient `better-auth.session_token` cookie for another account accompanies the `two_factor` challenge cookie, Better Auth verifies against the ambient session instead of the pending challenge. On non OAuth login, `frontend/pages/TwoFactor.tsx:160` also redirects ordinary users to `/admin`.
**Why it matters**: Once an ordinary user enables TOTP in `AccountDashboard`, subsequent logins in a multiple account browser leave that account missing from `/api/identity/accounts`, `/account`, and the OAuth chooser (where OAuth silently sees only the other active account), and challenge verification is not isolated from an ambient session cookie.
**Suggested fix**: Strip any ambient `better-auth.session_token` cookie when handling challenge verification with `better-auth.two_factor` (or isolate challenge completion from unrelated sessions), call `attachOrdinaryBrowserSessionToResponse` on ordinary account completion in `auth-two-factor.ts`, and route ordinary non OAuth logins in `TwoFactor.tsx` to `/account`.

## Major

### 🟠 Subject TOTP rate limit keys on mintable context handles and Better Auth skips lockout, `backend/src/routes/identity-totp.ts:22-31`
**Problem**: `totpSubjectRateLimit` keys by `digestToken("totp-rl-v1:" + contextHandle)` from `X-Identity-Context`, not by `userId`. Because `POST /api/identity/contexts` (`backend/src/routes/identity.ts:64`) has no rate limit, a holder of `swyra-browser` can mint fresh context handles to reset the 10 attempt limit repeatedly. Moreover, Better Auth skips `assertTwoFactorNotLocked` and `beginAttempt(5)` whenever `session.session` exists (`totp/index.mjs:174-203`), and `handleOwnerTotpDisable` (`identity-totp.ts:196-209`) validates TOTP before checking the user password.
**Why it matters**: An attacker with a browser proof cookie (and rotating IPs) can probe TOTP codes on `/api/identity/totp/verify` and `/api/identity/totp/disable` without hitting a per account quota or Better Auth lockout, and `/totp/enable` (`identity.ts:71`) exposes expensive password hashing without a per account limit.
**Suggested fix**: Enforce a per `userId` quota inside the TOTP handlers after resolving `verified.userId` (and on `/totp/enable`), rate limit `POST /api/identity/contexts`, and verify `body.password` before checking the TOTP code in `handleOwnerTotpDisable`.

### 🟠 Re calling `/api/identity/totp/enable` overwrites an active secret while claiming `pending: true`, `backend/src/routes/identity-totp.ts:49-76`
**Problem**: In Better Auth (`two-factor/index.mjs:149-158`), calling `enableTwoFactor` when `existingTwoFactor.verified === true` keeps `verified: true` and immediately overwrites `twoFactor.secret` and `twoFactor.backupCodes` in MongoDB. `handleOwnerTotpEnable` does not check whether TOTP is already enabled, and `frontend/components/AccountTotpPanel.tsx:60-79` always displays both Enable and Disable buttons because no TOTP status is exposed.
**Why it matters**: An enrolled user who clicks Enable TOTP with their password immediately destroys their working authenticator secret and backup codes before verifying the new code, locking themselves out if they abandon enrollment.
**Suggested fix**: Reject `/api/identity/totp/enable` with `409 ERR_TOTP_ALREADY_ENABLED` when `user.twoFactorEnabled === true` or `twoFactorDoc?.verified === true`, expose `totpEnabled` status on `/api/identity/contexts/me` (or a dedicated status endpoint), and render only the matching action in `AccountTotpPanel.tsx`.

### 🟠 Calling `/api/identity/totp/disable` during pending enrollment activates TOTP and fails with 401, `backend/src/routes/identity-totp.ts:184-213`
**Problem**: Line 186 checks only `if (!twoFactorDoc?.secret)` instead of verifying `twoFactorDoc?.verified === true` and `user.twoFactorEnabled === true`. If a user starts `/totp/enable` (`verified: false`) and then posts to `/totp/disable` with a valid code from the pending secret, `verifyTOTP` (`totp/index.mjs:205-223`) activates `user.twoFactorEnabled = true` and deletes `verified.sessionId`, causing the subsequent `disableTwoFactor` call (line 205, using the deleted session cookie) to fail with HTTP 401.
**Why it matters**: Submitting disable on a pending setup unexpectedly enables TOTP, destroys the active session, and leaves `browser_session_sets` out of sync.
**Suggested fix**: Require `userDoc?.twoFactorEnabled === true` and `twoFactorDoc?.verified === true` before claiming a step or calling `verifyTOTP` in `handleOwnerTotpDisable`.

### 🟠 Post verification registry update in `handleOwnerTotpVerify` lacks CAS fencing and fail closed handling, `backend/src/routes/identity-totp.ts:127-145`
**Problem**: Line 135 updates `browser_session_sets` filtering only by `{ setId: context.setId, "entries.entryId": verified.entryId }` without checking `revokedAt: null`, `entries.status: "active"`, or `entries.sessionId: verified.sessionId`, without incrementing `version` (unlike `browser-session-registry.ts`), and without checking `modifiedCount`. If the entry is concurrently signed out (`signOutBrowserEntry`) between `resolveOwnerDashboardContext` and line 135, the update attaches the newly minted session ID onto a `signed_out` entry. Also, if `rawSetCookie` parsing or `newSess` lookup fails, `activeSessionId` silently falls back to the deleted `verified.sessionId` and returns `200`, and re calling `/totp/verify` after `twoFactorDoc.verified === true` stamps `mfaVerifiedAt` without rotating the session.
**Why it matters**: Concurrent sign out and TOTP verification can leave an orphaned active session attached to a signed out entry, or break `browser_session_sets` silently on cookie parsing failure.
**Suggested fix**: Reject already verified TOTP docs (`twoFactorDoc.verified === true`), reuse `extractSessionTokenFromHeaders(res.headers)`, guard the `browser_session_sets` update with `revokedAt: null` and `$elemMatch: { entryId: verified.entryId, sessionId: verified.sessionId, status: "active" }` plus `$inc: { version: 1 }`, and delete the newly created session and fail closed if the update matches zero documents or `newSess` is missing.

### 🟠 Pre enrollment sessions retain full authority after TOTP enable and admins are not excluded from `/api/identity/totp/*`, `backend/src/routes/identity-totp.ts:85-233`
**Problem**: When an ordinary user enables TOTP via `handleOwnerTotpVerify`, only the current enrollment session is replaced; other existing password only sessions (`mfaVerifiedAt == null`) remain valid, and neither `session-adapter.ts:50-89` nor `oauth-selection.ts:109-160` nor `owner-contexts.ts` denies sessions lacking MFA once `userDoc.twoFactorEnabled === true`. Additionally, `identity-totp.ts` never checks `isOrdinaryRole(verified.role)`, so an account enrolled in `browser_session_sets` that was later promoted to `app-admin` (`app-invitations.ts:186`) can disable its mandatory TOTP via `/api/identity/totp/disable` without gateway trust or `requireRecentMfa`.
**Why it matters**: Pre enrollment password only sessions continue issuing OAuth codes and dashboard contexts without MFA (falling short of `docs/SECURITY.md` section 6 and AC-11), and promoted admins can mutate MFA state outside gated admin routes.
**Suggested fix**: Revoke other pre enrollment sessions on `handleOwnerTotpVerify` (or reject sessions with `mfaTime == null` when `userDoc.twoFactorEnabled === true` in `session-adapter.ts`), and reject non ordinary roles (`!isOrdinaryRole(verified.role)`) in `identity-totp.ts`.

### 🟠 Permissive assertions and missing test coverage for disable, login completion, replay, and UI flows, `backend/tests/security/p4-optional-user-totp.test.ts:124-178`
**Problem**: `p4-optional-user-totp.test.ts:175-176` asserts `disRes.status === 200 || disRes.status === 409` with an incorrect comment stating that reusing the same step for disable returns `409` (in fact `purpose` differs, so it returns `200`). It never verifies `twoFactorEnabled === false`, never checks whether the user's current session survived (which currently fails due to blocker 1), never checks revocation of other sessions or `oauthRefreshToken` / `oauth_token_families`, never checks that account B remains intact after disable, never asserts that the 9 losing concurrent requests returned `409`, never tests cross step replay within the 90 second window, and never completes login 2FA via `/api/auth/two-factor/verify-totp`. The new frontend UI in `AccountTotpPanel.tsx` and `AccountDashboard.tsx` also has zero unit or Playwright E2E coverage.
**Why it matters**: Permissive assertions masked critical bugs in `handleOwnerTotpDisable` and replay enforcement, and the user facing UI has no automated verification.
**Suggested fix**: Assert exact status codes and database state transitions for concurrency (`409`), cross step replay, disable (active session preservation, other session revocation, refresh family revocation, `twoFactorEnabled: false`, account B survival), negative inputs, login 2FA multi account integration, and add Playwright tests covering `AccountTotpPanel.tsx` on `/account`.

## Minor

### 🟡 `AccountTotpPanel` lacks cancel actions, local QR rendering, and safe URL parsing, `frontend/components/AccountTotpPanel.tsx:53-130`
**Problem**: `enrolling` and `disabling` states have no cancel button to return to `idle`, `enrolling` shows only the raw secret without rendering a local QR code (despite `qrcode.react` in `frontend/package.json:24` and `docs/AUTHENTICATION_FLOWS.md:130`), `new URL(totpURI)` on line 53 is unguarded against malformed strings, and `password` / `code` state is retained after `verifyEnrollment`.
**Why it matters**: Users cannot back out of an abandoned disable or enroll form without reloading and losing their in memory context, and a malformed `totpURI` would crash the component.
**Suggested fix**: Add Cancel buttons to `enrolling` and `disabling` views, render a local QR code from `totpURI` alongside the manual key, guard `new URL(totpURI)` in a `try/catch`, and clear sensitive form fields on transition.

### 🟡 `verify.md` contains duplicated P4 ledger entries and omits `562751a`, `docs/specs/0008-multi-account-identity-platform/verify.md:813-1009`
**Problem**: Lines 813 through 1009 repeat several P4 evidence sections multiple times (including four copies of `Slice P4 independent account and IP recovery rate limits`, all updated identically in `39209af`), and `562751a` adds no verification entry for `test:p4-user-totp`.
**Why it matters**: Duplicate ledger sections obscure which commit and command outputs apply to the active branch state.
**Suggested fix**: Deduplicate lines 813 through 1009 in `verify.md` and record honest evidence for `562751a` once the blocker fixes and tests run.

### 🟡 New rate limiters skip Redis and `/totp/enable` lacks a subject limit, `backend/src/routes/identity-totp.ts:15-31`
**Problem**: Neither `totpIpRateLimit` nor `totpSubjectRateLimit` nor `recoveryIpRateLimit` / `recoveryAccountRateLimit` sets `limiterName`, so all requests bypass Upstash Redis even when configured and hit MongoDB `rate_limits`. Additionally, `/api/identity/totp/enable` (`identity.ts:71`) lacks a per account limiter around expensive `scrypt` password checks, and `claimTotpTimeStep` (`totp-replay-guard.ts:38`) invokes unmemoized `ensureIdentityCollectionIndexes` (36 metadata calls) on every attempt.
**Why it matters**: Bypassing Redis and issuing 36 index calls per TOTP attempt adds unnecessary MongoDB load, and unthrottled password checking across rotating IPs weakens `/totp/enable`.
**Suggested fix**: Wire `limiterName` (or equivalent Redis limiters) where appropriate, add per `userId` throttling to `/totp/enable`, and memoize `ensureIdentityCollectionIndexes` per database instance.

### 🟡 `buildBoundSessionHeaders` omits `dontRememberToken` during session rotation, `backend/src/routes/identity-totp.ts:37-47`
**Problem**: `SignIn.tsx:189` hardcodes `rememberMe: false` (setting a 1 day session and `dontRememberToken`), whereas `buildBoundSessionHeaders` builds a cookie header with only `sessionToken`. When Better Auth rotates the session in `verifyTOTP` (`totp/index.mjs:210`), `dontRememberMe` evaluates to `false` (`internal-adapter.mjs:272`), extending the session lifetime from 1 day to 7 days.
**Why it matters**: Enrolling or disabling TOTP silently upgrades short sessions to 7 day persistent sessions.
**Suggested fix**: Derive `dontRememberMe` from the existing `session` record duration (or pass the matching `dontRememberToken` cookie) when constructing `buildBoundSessionHeaders`.
