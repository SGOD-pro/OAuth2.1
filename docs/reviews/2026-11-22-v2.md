## Summary

This update reconciles and corrects the OAuth V2 Slice P1b runtime enforcement specification in `docs/specs/0008-multi-account-identity-platform/0008-p1-client-policy-migration.md` and updates evidence descriptions in `docs/specs/0008-multi-account-identity-platform/verify.md`. The revised specification eliminates all protocol and naming contradictions: direct HTTP 400 errors are enforced for invalid client identity and redirect URI per RFC 6749 Section 3.1.2.4; error redirects strictly preserve state per RFC 6749 Section 4.1.2.1; PKCE S256 is required for confidential authorization code clients per OAuth 2.1 Section 4.1.1 and BCP 212; native loopback IP literals and ephemeral port handling are scoped strictly to native and development clients per RFC 8252 Section 7.3 with localhost documented separately as a developer fallback; token introspection validates current private membership returning active false upon revocation; actual database and classifier schema field names are used; unconditional binary rollback assumptions are replaced with a detailed compatibility matrix; concurrency safe membership boundaries across independent HTTP request lifecycles are defined; and mocked engine responses in Worker B are explicitly labeled in the verification ledger.

## Findings and Assessment

1. Protocol Error Alignment: Authorization errors for missing or invalid client identity or redirect URI return direct HTTP 400 errors without redirecting, adhering strictly to RFC 6749 Section 3.1.2.4. Permitted error redirects (`access_denied`, `invalid_request`) strictly preserve the client state parameter per RFC 6749 Section 4.1.2.1. Standard authentication challenge headers (`WWW-Authenticate: Basic realm="OAuth"` on token Basic failure and `WWW-Authenticate: Bearer error="invalid_token"` on UserInfo failure) are explicitly defined.
2. Mandatory PKCE for Confidential Code Grants: In alignment with OAuth 2.1 Section 4.1.1 and RFC 9700 (BCP 212), PKCE S256 is required for all clients executing authorization code flows, including confidential clients. The Next.js BFF consumer recipe and acceptance criteria (AC-P1B-03) are updated to require PKCE S256 challenge on authorization and verifier on code exchange.
3. Native Loopback Redirect Scoping: Native production loopback callbacks are reconciled. Per RFC 8252 Section 7.3, ephemeral variable ports on loopback IP literals (`127.0.0.1`, `[::1]`) are restricted strictly to native clients (`application_type: "native"`) and development clients (`isDev: true`). Localhost is documented separately as a developer compatibility fallback per RFC 8252 Section 8.3, and production web applications strictly require HTTPS.
4. Introspection Private Membership Validation: Token introspection (`POST /api/auth/oauth2/introspect`) strictly enforces confidential client authentication, verifies calling client authority, and validates current user private tenant membership. Revoked or deactivated private access returns HTTP 200 `{ active: false }`, matching the UserInfo HTTP 403 forbidden and refresh HTTP 401 invalid grant outcomes.
5. Accurate Field and Schema Names: The specification replaces non existent field names with actual codebase types: `classification === "AMBIGUOUS"` or `isAmbiguous === true` per `client-policy-types.ts`, and `status: "revoked"` with `revokedAt: new Date()` per `token-families.ts`.
6. Deployment Rollback Compatibility Matrix: Unconditional binary rollback assumptions are replaced with a complete compatibility matrix covering all client classes (Clean Classes A, B, C, E, and Ambiguous Class D), changed credentials, existing token families, and mixed version rolling deployments. The matrix explicitly states when rollback requires a compatible patched binary or re provisioning credentials.
7. Concurrency Safe Membership Boundaries: Browser authorization and backchannel token code exchange are recognized as independent HTTP request boundaries. The specification clarifies that token exchange failures must never execute blind deletes on `user_app_registrations`, protecting pre existing, concurrent, and explicit memberships. Modern open access bypass eliminates ambient database writes completely.
8. Engine Support vs Runtime Wrappers and Evidence Honesty: Verified installed engine versions (`@better-auth/oauth-provider` v1.6.10, `@better-auth/core` 1.7.1) manage base collections and schemas, while custom runtime wrappers enforce policy dimensions, PKCE, and refresh rotation fencing. In `verify.md`, Worker B token minting mock (`authProvider.handler`) in `refresh-lease-fencing.test.ts` is explicitly labeled alongside live MongoDB CAS lease acquisition and rotation fencing.
