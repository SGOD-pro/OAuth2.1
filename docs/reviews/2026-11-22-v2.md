## Minor
### 🟡 Non 200 refresh token response retains rotation lock for 15 seconds, `backend/src/routes/auth-token-refresh.ts:272`
**Problem**: When `authProvider.handler(reqToForward)` returns a non 200 HTTP response (such as an expired session or invalid grant), the compare and swap rotation lock (`rotating: true`) on `oauth_token_families` is not immediately cleared.
**Why it matters**: The token family document retains `rotating: true` until the 15 second stale lock threshold expires. Any immediate retry by the client during that 15 second window receives a confusing error stating that the refresh token was already consumed or is currently being rotated, rather than the true failure reason.
**Suggested fix**: In `handleRefreshTokenGrant`, add a cleanup call in a finally block or before returning non 200 responses that resets `rotating: false` on the active token family.

### 🟡 Loopback redirect URIs rejected for production native clients, `backend/src/identity/client-policy.ts:89`
**Problem**: The redirect URI validator rejects `http:` loopback redirect URIs whenever `isDev` is false, regardless of whether the client `application_type` is `native`.
**Why it matters**: RFC 8252 permits native applications to use HTTP loopback redirect URIs with dynamic ports in production. Auditing legitimate production native clients will flag them with `INVALID_REDIRECT_URI` unless they are marked with `isDev`.
**Suggested fix**: Permit `http:` loopback redirect URIs if either `isDev` is true or `application_type` equals `native`.
