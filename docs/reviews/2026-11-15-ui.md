## Summary
This change delivers substantial improvements to audit logging, session isolation, and admin console UX. It fixes a critical authentication boundary violation where MFA first-factor logins were prematurely logged as completed sign-ins and registered to public applications, adds database-side correlation and unified aggregation for logs with server-side pagination, and introduces robust concurrency and race guards to the admin Zustand store. One major contract issue must be resolved before merge: custom pagination response headers on `/api/admin/logs` are not exposed via CORS `Access-Control-Expose-Headers`, which will break cross-origin consumer/admin pagination controls.

## Major
### 🟠 Missing CORS Expose-Headers for Pagination Metadata, `backend/src/middleware/cors.ts:97` and `backend/src/routes/admin.ts:702`
**Problem**: `/api/admin/logs` returns pagination metadata exclusively through HTTP response headers (`X-Total-Count`, `X-Page`, `X-Limit`, `X-Total-Pages`), and `frontend/lib/adminStore.ts:311-314` reads them using `res.headers.get()`. However, `applyCorsHeaders` in `cors.ts` does not declare `Access-Control-Expose-Headers`.
**Why it matters**: In the Fetch API specification, cross-origin responses cannot read custom headers unless they are explicitly enumerated in `Access-Control-Expose-Headers`. While this works when proxied over the same origin in local development or unified Vercel domains, any decoupled or cross-origin access will receive `null` from `res.headers.get()`, causing `totalCount` to default to `0` and `totalPages` to `1`, breaking pagination controls and table entry counts.
**Suggested fix**: Add `Access-Control-Expose-Headers: X-Total-Count, X-Page, X-Limit, X-Total-Pages` to `applyCorsHeaders` in `backend/src/middleware/cors.ts`, or adopt the envelope pattern already used by `/v2/logs` to return pagination metadata within the JSON response body.

## Minor
### 🟡 Public Application Registration Skipped on MFA Verification, `backend/src/routes/auth.ts:2480`
**Problem**: When a user with two-factor authentication logs in, `/sign-in/email` correctly halts early to avoid registering the user before MFA finishes. However, in `/two-factor/verify-totp` (and `/two-factor/verify-backup-code`), `user_app_registrations` is not updated when the second factor succeeds.
**Why it matters**: Under AGENTS.md § Supported Application Configurations (Rule A), first login to a public application must record membership in `user_app_registrations`. Users with 2FA enabled who log into a public application will not have their registration recorded upon successful login.
**Suggested fix**: In `auth.post("/two-factor/verify-totp")` and `auth.post("/two-factor/verify-backup-code")`, when `isSuccess` is true and the bound OAuth client is public, perform an idempotent upsert into `user_app_registrations` matching the single-factor login behavior.

### 🟡 Unbounded Sub-Pipeline Lookup on Active Sessions, `backend/src/routes/admin.ts:456`
**Problem**: The `unmappedSessionPipeline` executes a `$lookup` into `auth_events` for every session document in the `session` collection to filter out active sessions that already have an associated auth event.
**Why it matters**: In environments with high concurrent active session counts (tens of thousands of users), executing a `$lookup` sub-pipeline per session on every logs query and count aggregation can increase MongoDB query latency and memory consumption.
**Suggested fix**: Ensure the `session` collection has an index on `createdAt: -1` and restrict the unmapped session lookup to sessions created within the requested date window or with a limit, or mark correlated sessions with a boolean flag or TTL window.

- ⚪ `frontend/pages/admin/AdminLogs.tsx:183`: If the total logs count shrinks (e.g. from an active filter change or deletion) such that `page > totalPages`, `page` is not clamped, leaving the user on an out-of-range empty page until they manually paginate back.

Leaving `indicatorStyle.ready` as false when `idx === -1` would prevent displaying a misleading active indicator on unmatched routes.
