## Summary
This independent review evaluated the OAuth 2.1 remediation on branch bug-fix.
The review inspected the code diff against main, the canonical documentation, specifications 0001 through 0005, and actual test executions.
While significant work was completed to address server error fail closed handling, real key self healing, and origin derivation, several critical issues require remediation before this work can merge safely.
In particular, the refresh token rollback mechanism is non atomic and can resurrect revoked credentials through an upsert.
Furthermore, the test suite labeled as consumer end to end testing is an in process simulation rather than a multi process browser test, and the test suite labeled as IdP restart only clears memory caches.

## Blockers

### 🔴 Refresh Token Resurrection via Upsert in Rollback, `backend/src/routes/auth.ts:1214-1227`
**Problem**: In the refresh token path, when RS256 access token minting fails, the rollback logic attempts to restore the previous refresh token by executing `database.collection("oauthRefreshToken").updateOne(..., { $set: { revoked: null, rotatedAt: null }, $setOnInsert: { ... } }, { upsert: true })`.
**Why it matters**: If the incoming refresh token was already revoked, deleted by an administrative session termination, or purged by a cascade revocation, the `{ upsert: true }` option inserts a brand new valid refresh token with a fresh 30 day expiration date. This resurrects an invalid or deleted credential from the dead, creating a severe credential revival vulnerability.
**Suggested fix**: Remove `{ upsert: true }` entirely from this update. The update must only touch an existing document if it was active immediately prior to this rotation attempt.

## Major

### 🟠 Non Atomic Rollback Across Multiple Collections, `backend/src/routes/auth.ts:1184-1228`
**Problem**: The rollback logic on token minting failure executes four separate uncoordinated MongoDB operations: deleting the newly minted refresh token, deleting the newly minted access token, updating the token family document, and updating the old refresh token record. Each operation is individually caught with an empty catch block.
**Why it matters**: If the process terminates, times out, or encounters a transient database error between these calls, the database enters a split state. The token family record and the Better Auth refresh token collection will disagree on which token hash is active and whether it is consumed. Furthermore, the family update at line 1204 matches `{ familyId, activeTokenHash: newHash }` without checking `{ status: "active" }`, meaning a family revoked concurrently by another security event will have its active token hash reset and its rotating flag cleared.
**Suggested fix**: Wrap multi collection state changes in a MongoDB transaction when available, or structure the family status transition so that revoked families cannot be modified, and ensure errors during rollback are logged rather than silently discarded.

### 🟠 Consumer End to End Test Is In Process Simulation, `backend/tests/e2e/local-consumer-e2e.test.ts:1-804`
**Problem**: The test file named `local-consumer-e2e.test.ts` exercises the Hono `app.request()` routing pipeline in process. Neither `test/next-app` nor `test/react-express-app` is launched as a network server, and no real browser or HTTP client process is started. In addition, neither consumer app has its dependencies installed in `node_modules`.
**Why it matters**: In process route calls simulate HTTP headers and cookies in plain script variables. They do not test real browser cookie jar behavior, Lax or Strict SameSite cookie isolation across distinct origins, actual network socket timeouts, or framework specific route handlers under live HTTP traffic.
**Suggested fix**: Clearly document `local-consumer-e2e.test.ts` as an in process protocol test suite, and provide an automated fixture runner that installs consumer dependencies and launches real network servers on loopback ports for browser testing.

### 🟠 IdP Process Restart Test Is In Memory Cache Eviction Simulation, `backend/tests/e2e/local-consumer-e2e.test.ts:739-742`
**Problem**: In Flow 10, the test simulates an IdP restart by calling `clearSigningKeyCacheForTesting()` and `clearPublicKeyCacheForTesting()`.
**Why it matters**: Clearing two in memory cache variables within an already running Node.js process does not test an actual process restart. A real process restart reloads modules from disk, re-establishes MongoDB connection pools, initializes Better Auth singletons, and resets any ephemeral in memory state.
**Suggested fix**: Implement a test that spawns a child Node.js process running the actual server, issues tokens, terminates the child process, spawns a new child process against the same database, and verifies token verification and rotation.

### 🟠 Consumer Refresh Coordination Is Limited to Single Process Memory, `test/next-app/src/lib/oauth.ts:85-106` and `test/react-express-app/backend/src/middleware/auth.ts:24-35`
**Problem**: Both consumer implementations coordinate concurrent token refreshes using an in memory JavaScript `Map` of promises.
**Why it matters**: This in memory lock deduplicates requests within a single Node.js process thread only. In a multi process architecture, such as cluster mode, container replicas, or serverless instances, two consumer processes sharing a session will still issue concurrent refresh requests to the IdP. When this occurs, the IdP grace window prevents cascade family revocation, but the second process receives HTTP 400 invalid grant and fails. Without shared session storage, the second process cannot retrieve the new credentials and drops the user session.
**Suggested fix**: Document the exact concurrency boundaries in consumer integration guides. If multi process consumers share a session, they must use centralized session storage such as Redis or a shared database with a distributed refresh mutex.

### 🟠 Security Test Suite Requires External Docker MongoDB and Fails Locally, `backend/package.json:48`
**Problem**: Running `npm run test:all-security` locally fails immediately. Without environment variables, it crashes on Zod schema validation in `src/config/env.ts:12`. When environment variables are supplied, it attempts to connect to `mongodb://127.0.0.1:27017/test_security` and fails with connection refused because the test files do not use `MongoMemoryServer`.
**Why it matters**: Local developers cannot run the full security test suite before pushing code, creating complete reliance on GitHub Actions CI Docker services.
**Suggested fix**: Update `test:all-security` test runners to either spin up disposable in memory MongoDB instances or provide a local runner script that starts a containerized database automatically.

## Minor

### 🟡 Authorization Code Exchange Is Unrecoverable on Mint Failure, `backend/src/routes/auth.ts:1383-1420`
**Problem**: When RS256 token minting fails during authorization code exchange, the rollback logic deletes the issued tokens. However, the authorization code has already been consumed by Better Auth.
**Why it matters**: The client receives HTTP 500 server error and cannot retry the token exchange with the same code. The user must restart authentication from the beginning.
**Suggested fix**: Document this behavior as a known fail closed consequence of the single use code specification.
