## Summary

This branch delivers five substantial fixes: cold-start Super Admin identity lockout prevention, token-family rotation race condition hardening (stale-lock reclaim + atomic single-winner semantics), JWT minting fail-closed hardening with partial token purge on failure, per-`kid` JWKS key resolution with newest-key fallback, and a large ponytail cleanup pass (dead Redis write functions removed, unbounded user scan replaced, dead scripts deleted, `docker-compose.yml` corrected). Two issues below require attention before merge: the Express consumer middleware skips cryptographic `iss` verification on the first JWT verification path, and the Next.js BFF route trusts a cookie token without verifying its signature.

## Major

### 🟠 Express middleware: `jwtVerify` called without `issuer` option — `iss` not cryptographically verified, `test/react-express-app/backend/src/middleware/auth.ts:202`

**Problem**: `jwtVerify(token, key)` at line 202 is called with no options object. The code then does a manual string comparison on `payload.client_id || payload.azp || payload.aud` (lines 205-211) to check the client, but it never verifies the `iss` (issuer) claim against `AUTH_ISSUER`. A JWT issued by any RS256 key that the JWKS endpoint happens to resolve — or by a third party whose key the server has accidentally cached — would pass the cryptographic check and reach the manual `client_id` comparison without issuer validation.

Compare this to the Next.js BFF at `test/next-app/src/app/api/secure-data/route.ts:52-55` which correctly passes `{ issuer, audience: clientId }` to `jwtVerify`. The Express middleware should do the same, dropping the downstream manual comparison.

**Why it matters**: AGENTS.md rule #9 states `iss` MUST be validated against `AUTH_ISSUER`. Without this, a token from a different issuer with a matching key would be accepted. In a multi-tenant or multi-IdP environment, this is a cross-tenant authentication bypass.

**Suggested fix**: Pass `{ issuer, audience: clientId }` as the third argument to `jwtVerify(token, key, { issuer, audience: clientId })`. Remove or tighten the subsequent manual `tokenClientId` comparison — let jose enforce both claims atomically.

### 🟠 Next.js BFF secure-data route: cookie-based auth path skips JWT signature verification, `test/next-app/src/app/api/secure-data/route.ts:39-43`

**Problem**: When a request arrives with an `auth_session` cookie, the route reads `session.tokens.access_token` and sets `isAuthenticated = true` (line 40) without calling `jwtVerify`. The Bearer token path at lines 47-61 correctly calls `jwtVerify` with `{ issuer, audience }`, but the cookie path does not. Any request carrying a forged or replayed `auth_session` cookie — for example, if an attacker has stolen or tampered with the cookie content — is accepted as authenticated.

Note the callback route at `test/next-app/src/app/api/auth/callback/route.ts` does verify `state` before setting the cookie, which is correct for the login flow. But the secure-data route itself does not re-verify the token inside the cookie on every request.

**Why it matters**: The secure-data route is the access-controlled resource. Trusting a cookie value without verifying its contained JWT means the authorization check can be bypassed by crafting the cookie. In a BFF that stores tokens in HttpOnly cookies and exposes API endpoints, every protected endpoint should cryptographically verify the access token it finds in the session cookie, not merely check that it is a non-empty string.

**Suggested fix**: Call `jwtVerify(session.tokens.access_token, getJWKS(issuer), { issuer, audience: clientId })` in the cookie path before setting `isAuthenticated = true`. Use the same `issuer` / `clientId` from `requireEnv`. If verification throws, return 401.

## Minor

### 🟡 `verifyGatewaySecret` dev bypass reads remote address through multiple heuristic paths — one can be spoofed via `x-forwarded-host`, `backend/src/middleware/admin-auth.ts` (dev bypass block)

**Problem**: The development loopback bypass checks `remoteAddress` from the socket (good, not spoofable) but also checks `requestHost` which is read from `x-forwarded-host` before `host` (lines in the dev bypass block). `x-forwarded-host` is set by the client and is not trustworthy unless the server sits behind a proxy that strips it. A request from a non-loopback IP that sets `x-forwarded-host: localhost` would pass both the `remoteAddress` check (which would block it) and the `requestHost` check.

Looking at the logic more carefully: `remoteAddress` is checked first and must be loopback or absent for the bypass to proceed. If `remoteAddress` is a non-loopback address, `!isLoopbackHost(remoteAddress)` is true and the function returns `false`. The `x-forwarded-host` path is only reached when `remoteAddress` is absent or is a loopback address. In a typical server environment, `remoteAddress` is always set, so the risk is low in practice.

**Why it matters**: This bypass is production-guarded (`isProduction` check), so the risk is limited to development mode. However, the layered heuristics add complexity that could mislead a future developer.

**Suggested fix**: Add a comment explaining that `requestHost` is only evaluated after the `remoteAddress` loopback check has already passed, making the `x-forwarded-host` path safe in context. Consider removing the `x-forwarded-host` lookup from this dev bypass entirely — if the socket's `remoteAddress` is loopback, the host header is redundant.

### 🟡 `patch /clients/:id` skips `validateOAuthClientConfiguration` when only `name` or `skip_consent` changes, but `applicationType` falls back to the raw DB value, `backend/src/routes/admin.ts:638-655`

**Problem**: The new conditional validation block skips `validateOAuthClientConfiguration` unless `hasNewRedirectUris || targetIsDev changed || hasNewAllowedOrigins`. When validation is skipped, `applicationType` is read from `oldClient.applicationType || oldClient.application_type || "web"`. If the stored DB document has neither field (a client created before this field was introduced), `applicationType` silently defaults to `"web"`. This is probably fine in practice since the field was always written on create, but the fallback could yield an incorrect `application_type` on update without a warning.

**Why it matters**: `application_type` governs redirect URI validation. A wrong default could allow updating to a configuration that passes the update path but would fail a fresh validation. Low risk because the skip condition is narrow.

**Suggested fix**: Log a warning when `applicationType` falls back to the default `"web"` due to missing stored value.

### 🟡 `resolveUserRoleForClient` in `auth.ts` and `checkUserIsClientAdmin` in `admin-auth.ts` contain near-identical DB query patterns — duplicated logic, `backend/src/routes/auth.ts` and `backend/src/middleware/admin-auth.ts`

**Problem**: Both functions query `app_admins` and `user_app_registrations` with the same `$or` structure (userId string + `_id` ObjectId + email for `app_admins`, userId string + `_id` ObjectId for registrations). The logic was clearly co-developed but now lives in two files, 50+ lines each, with slightly different field names and return types.

**Why it matters**: Any future change to the admin-lookup semantics (new fields, new conditions) must be made in two places, with a high risk of them diverging. Not a blocker, but this will bite the team.

**Suggested fix**: Extract a shared `lookupAdminStatus(database, userDoc, clientId): Promise<{isAdmin, scopedClientId}>` utility into `backend/src/utils/admin-sync.ts` or a new `backend/src/utils/role.ts`. Both callers import it.

## Strengths

- The Super Admin lockout fix in `admin-sync.ts` is surgical and correct: the guard `if (!isSuperAdmin)` wraps every mutation (role update, account upsert, ban flag) so a Super Admin's primary credentials are never overwritten by an app-admin provisioning call. The `user_app_registrations` upsert is promoted to an unconditional `updateOne` with `{ upsert: true }` which correctly handles the first-time and idempotent cases in a single round trip.
- Token rotation stale-lock reclaim (`rotatingAt < staleLockThreshold`) is a correct and well-scoped fix for the race window where a crashed rotation handler leaves a `rotating: true` lock permanently. The 15-second threshold is reasonable for a network-bounded operation.
- Unit test suite is thorough: `admin-scoping.test.ts` (12 tests), `runtime-resilience.test.ts` (7 tests), `gateway-pipeline.test.ts` (11 tests), `dev-isolation.test.ts`, and `config-simplification.test.ts` all pass cleanly and cover the branching logic added in this branch.
- `deriveAllowedOriginsFromRedirectUris` is a clean, safe utility: non-HTTP schemes are silently skipped, invalid URLs are caught, and origins are deduplicated. Both backend and frontend implementations are tested for parity.
